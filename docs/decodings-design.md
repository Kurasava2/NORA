# Расшифровки ГСМ — архитектурный проект

Статус: рабочий проект перед изменением схемы данных.

## Цель

Встроить в существующее приложение единый модуль «Расшифровки» без отдельной базы и без копирования Excel-интерфейса.

Цепочка:

Путевой лист → ведомость автомобиля → расшифровка подразделения → контроль партий/плотностей → Excel/печать → переходящий остаток.

## Что уже есть и переиспользуется

- `state.periods` и `period.reportMonth` — месяцы/периоды.
- `period.statements` — автомобильные ведомости.
- `statement.trips` — путевые листы с датами, одометром, моточасами и движением материалов.
- `state.vehicles` — карточки машин.
- `state.catalog` — единый справочник материалов.
- `totals(statement)` — начало/получено/расход/конец по материалам.
- `validateStatement()` — проверки исходных ведомостей.
- `migrateState()` — единая миграция данных.
- `.gsmbackup` — резервирует весь application state целиком.
- существующие `Card`, `PageHead`, `Badge`, `Modal`, таблицы, уведомления и навигация.

Отдельную базу расшифровок и отдельный backup-формат создавать не нужно.

## Важное ограничение текущей ведомости

Сейчас материальный баланс путёвки:

`start + received - spent = end`

Отдельного поля «сдано» в текущей модели нет. Расшифровка не должна выдумывать его. До появления подтверждённого источника `surrendered` равен нулю или отсутствует. Если официальная форма требует отдельный возврат/сдачу, это должно быть отдельное явное поле/операция с миграцией и проверками.

## Предлагаемая модель данных

После утверждения схема данных повышается отдельной миграцией. Backup format v1 менять не нужно: envelope уже хранит `dataSchemaVersion` и весь `state`.

### `state.decodings`

Массив документов расшифровки:

```js
{
  id,
  periodId,
  mode, // form63 | form33 | form31
  createdAt,
  updatedAt,
  sourceFingerprint,
  sourceSnapshot,
  openingLotBalances,
  status,
  finalizedAt
}
```

`sourceSnapshot` содержит только необходимые неизменяемые данные из ведомостей на момент формирования: vehicleId, statementId, последний путевой лист, одометр/моточасы, материал, начало, получено, расход, конец и вычисляемые нормативные показатели.

Если исходные ведомости изменились, новый fingerprint не совпадает — документ получает состояние `source-stale`. Никаких обратных изменений ведомости из расшифровки.

### `state.densityLots`

Партии имеют стабильные ID и могут переживать несколько месяцев:

```js
{
  id,
  materialName,
  densityText,
  volumeText,
  date,
  sourceType, // receipt | carry | manual-adjustment
  sourcePeriodId,
  parentLotId,
  note,
  createdAt
}
```

Плотность и исходный объём сохраняются в введённом десятичном виде без преждевременного округления.

Переходящий остаток не создаёт «новую плотность». Следующий месяц ссылается на исходную партию через `lotId`/`parentLotId` и переносит точный остаток.

### `state.densityAllocations`

```js
{
  id,
  decodingId,
  statementId,
  vehicleId,
  materialName,
  lotId,
  kind, // opening | received | spent | surrendered | closing
  litersText,
  source, // auto | manual
  updatedAt
}
```

Одна машина и один материал могут иметь любое количество строк распределения по разным партиям.

UI сначала показывает понятный пользователю расход, например 300 л @ 0,827 + 250 л @ 0,829, но движок может хранить также разложение начала/получения/конца. Это необходимо, чтобы плотность остатка следующего месяца не терялась.

### `state.decodingContainers`

```js
{
  id,
  decodingId,
  materialName,
  type,
  quantityText,
  massKgText,
  note
}
```

Тара не смешивается с литровыми партиями.

## Почему партии глобальные, а документ месячный

Расшифровка относится к конкретному `periodId`, но партия физически может начаться в апреле и закончиться в мае/июне. Поэтому lot ID должен быть стабильным между документами.

При формировании нового месяца:

1. ищется предыдущая финализированная расшифровка этого режима;
2. её остатки по lot ID становятся `openingLotBalances` нового месяца;
3. новые поступления создают новые lot ID;
4. если предыдущий документ позже изменён, следующий помечается `carry-stale`, а не тихо переписывается.

## Автораспределение

FIFO — только предложение.

Движок строит предлагаемое распределение по дате партии и предыдущему остатку. Пользователь может изменить любое распределение вручную. После ручной правки строка получает `source: manual` и повторный AUTO не должен молча её затереть.

Для более точного предложения можно использовать уже имеющуюся последовательность путёвок по датам: UI остаётся месячным, но движок способен пройти `statement.trips` хронологически.

## Точность

Внутри расчётов не округлять массу.

`kg = liters × density`

Для надёжного десятичного учёта планируется отдельный decimal helper на строковых значениях/масштабированных целых, а не ранний `Math.round()`.

Форматирование (целые кг, десятые, тысячные) выполняется только конкретным экспортным шаблоном.

## Проверки

Критические:

- исходная ведомость содержит ошибки;
- `start + received - surrendered - spent != end` с учётом доступных полей;
- сумма распределений по плотностям не равна исходному объёму;
- распределение превышает доступный объём партии;
- отрицательный остаток партии;
- потерян lot ID переходящего остатка;
- изменился source fingerprint;
- изменился предыдущий финализированный остаток (`carry-stale`).

Предупреждения:

- ручное распределение отличается от FIFO;
- партия без даты/документа-источника;
- плотность вне разумного диапазона для выбранного материала (после определения диапазонов по типам).

## Экран

Sidebar: новый `Расшифровки` рядом с периодами/автомобилями.

Главный экран:

- выбор периода;
- «Сформировать из ведомостей»;
- KPI: машин, материалов, плотностей, ошибок;
- карточки материалов с начало/получено/расход/конец;
- статусы готовности.

Материал:

- read-only таблица машин из source snapshot;
- переключатели плотностей;
- `+ Партия`;
- `Распределить автоматически`;
- `Проверить`;
- детализация распределения в modal/drawer без копирования строк машины.

Данные из ведомости визуально read-only. Изменения только через исходную ведомость.

## Режимы

Общая оболочка `Decodings` и отдельные engines:

- `Form63Engine` — топливо/плотности/партии;
- `Form33Engine` — ОЖ, дни эксплуатации, ёмкость системы, проценты и долив;
- `Form31Engine` — масла/спецжидкости.

Не создавать четыре независимых UI-модуля: общие навигация, source snapshot, validation, export shell и backup.

## Порядок реализации

1. исправить prefill новой путёвки: переносить только `odoStart`, `odoEnd` оставить пустым;

3. добавить тесты агрегирования и decimal helper;
4. после проверки поднять `STORAGE_VERSION` одной миграцией и добавить пустые массивы новых сущностей;
5. добавить навигацию и read-only экран расшифровки;
6. добавить партии/плотности;
7. добавить FIFO + manual override;
8. добавить carry между месяцами;
9. добавить validation gate;
10. только затем подключать официальный Excel/печать по реальному шаблону.
